## 导读：三个正面回答

**Q1：这一轮到底要做什么？**
不是再加一个功能，是换一个**产出物**。现在的系统输出的是"一次执行的响应"，用户要的是一句能存档、能给别人看、能喂给别的系统的话：**这批提交，敢不敢上**。所以原子单位从"一次执行"换成"一张提测单"，而这张单子的每一行都必须点得回证据——不是生成的文字，是带证据链接的结构化数据。

**Q2：凭什么这是我们做得到、Postman/数据库工具做不到的？**
因为结论单要回答的三件事，各自都需要一件它们手里没有的东西：

| 结论单要回答 | 需要的独有资产 | 为什么别人没有 |
|---|---|---|
| "这批提交动了哪些东西" | 代码↔语句↔接口↔提交 四向映射 | 抓包工具只看见流量，不知道 1 行 SQL 改动落在哪条语句上（`commit_targets` 的 basis=line 就是为此而生） |
| "测过没测过、上次什么结果" | 带 commit_id 的请求/响应快照（`test_runs`） | 接口工具的 history 不绑代码版本，无法回答"在哪个版本上通过的" |
| "失败是真失败还是数据变了" | 目标库只读通道 + 元数据（`table_meta`/字典项） | 只有能直连库做只读校验的系统，才能证明"当初那条卡号 12345 现在状态不是 A 了" |

Postman 与 DBeaver 各自能做到其中一件，**没有一件能做到三件，因为把它们拼起来的那个"变更事件流"只有本系统有**。

**Q3：跟已有的"起飞检查单"是什么关系？**
是**升级**，不是另起一套。已经跑通的这套（`ReleaseController.java`）方向对，但有四个缺口，正好是本文要补的：

| 缺口 | 现状（证据） | 后果 |
|---|---|---|
| 粒度错 | 快照按 `file_changes` 逐文件摊（ReleaseController.java:51-64），不到"目标" | 改 1 个 mapper 文件里的 3 条语句，单子给你 1 行"这个文件"——不知道该测哪条 |
| 无证据 | 条目只有 `testStatus` 字符串（:61），没有任何 run_id | 别人问"你说测过了，哪次测的？"你答不出来 |
| 无分类 | 结论只有 READY/BLOCKED 二值（:120） | 失败分不清是代码坏了还是数据漂移了，这正是测试中最耗时的判断 |
| 不透明 | 整份单子是 `snapshot_json` 一个 blob，导出是字符串拼 HTML（:181-185） | 喂不了别的系统；也看不出"哪些目标没被任何用例命中"（空白不可见） |

## §1 差异化判据：一把尺（后面所有点子都拿它量）

一个功能值不值得做，看它同时满足几条：

1. **吃掉 ≥2 样独有资产**（六样：四向映射 / 只读库通道+元数据 / 带 commit_id 的执行快照 / 版本化知识资产 / 变更事件流 / 内网离线流程）。吃掉 0～1 样的，多半是同质化。
2. **把人的"判断"变成人的"确认"**，而不是把点减少几个。前者错了人能拦；后者错了直接进报告。
3. **留下会增值的资产**。做完之后系统里多了一份可复用数据（教训库/基准/映射精度），还是只多了一次性输出。

三条全中 → 做；中一条 → 除非它是前一条的地基，否则不做；一条不中 → 记入"明确不做"。

自检过的反例（同质化，已排除）：更花哨的请求编辑器、响应树美化、多语言解析大饼、场景矩阵自动生成。

## §2 原子单位、状态机与不可变性

**提测单（Report）**：一个项目 + 一个环境 + 一段提交区间（含端点）= 一张单。区间语义沿用现有 `release_checklists.from_revision/to_revision`，不另造概念。

**版本报告**：若干张提测单（跨仓库/跨模块）的汇总，仍是一张单，`kind='version_report'`。它的结论行**只是指向子单的引用**（存子单 report_id），不在自己内部重算也不复制行内容——避免"汇总和明细不一致"这类 bug。子单改判，汇总自然跟着变；汇总页上必须显示"本行来自第 N 号子单"。

**状态机**：`draft`（草稿，可反复重算）→ `issued`（已出，快照固化，任何人不再改）→ `superseded`（被后续版本取代）。

**改一版怎么出**：`issued` 的单子**永不修改**。要改结论就出新单，`supersedes_id` 指回旧单，旧单转 `superseded`。这样"我上周说可以上、这周说不行"两个事实都在，追责与免责才成立——这也是用户选"要留档成上线依据"的直接推论。

**既有的签字能力一格都不许丢，但时序要收紧**：检查单现在能逐条"跳过（必须填理由）"并回写状态（ReleaseController.java:126-151）。升级后这套动作原样保留，只是作用对象从"文件条目"变成"结论行"，理由落进 `overrides_json` 的同一份留痕里（跳过也是一种改判）。唯一变严的地方：**签字只在 `draft` 期有效**，`issued` 之后不再改这张单（现有实现在出单后仍 UPDATE `snapshot_json`，:146——那正是"上线依据会被事后悄悄改掉"的洞，与 §2 的不可变性直接冲突）。要改结论走 §2 的出 v2。

**版本间差异只做展示**：任何两版之间"哪几行变了"是读取期现算的视图，**绝不落库成"差异记录"**。理由（本轮定的丙方案）：diff 一旦落库，就有两份互相可能不一致的事实；而"上线依据"必须只有一份、且不可重算。

## §3 数据层：在既有表上升级

### 3.1 `release_checklists` 补列（不新建 header 表）

```
kind          TEXT NOT NULL DEFAULT 'checklist'   -- checklist | report | version_report
env_id        INTEGER
status        TEXT NOT NULL DEFAULT 'draft'        -- draft | issued | superseded
fingerprint   TEXT                                  -- §3.4 指纹，出单那刻算死
supersedes_id INTEGER
issued_at     TEXT
```
老数据不需要任何 UPDATE 脚本：新列的默认值天然让历史条目落在 `kind='checklist'` / `status='issued'`（它们本来就是他手工导出去存档的既成事实）。历史时间戳一律不猜、不回填。

### 3.2 新增 `report_rows`（结论行，一行 = 一个目标在这张单里的结论）

```
report_id, target_type, target_id, commit_ids(该目标被区间内哪些提交动过),
basis(line|file|none),                     -- 归因精度，必须透出，不许假装都是行级
case_id, run_id,                           -- 证据指针：点得回哪条用例、哪次执行
status(pass|fail|blocked|na|pending),
classification(code|data_drift|env|unknown),
classify_evidence,                          -- 分类依据原文（只读校验证明了什么）
overrides_json                              -- 改判留痕：[{by,at,from,to,reason}]，人改的不覆盖系统判的
```

### 3.3 新增 `report_gaps`（空白与风险声明）

```
report_id, gap_type(no_case|no_commit_learned|premise_unverified|env_unreachable|value_expired),
target_type, target_id, subject, note, suggested_action
```
**空白是一等公民，不是"没数据"**。零用例的目标、算不出归因的提交、环境没跑成的整单，都必须在这里点名——这是全绿报告骗不了人的机制。

### 3.4 指纹（结论成立的前提条件）

出单那刻算死、逐字显示在报告上：

- 代码版本：区间起止 commit_id + 各仓库 revision
- 库结构版本：本次用到的表的 `table_meta` 结构指纹集合（沿用现有 schema_hash 语义）
- 通道版本：用到的知识包/服务字典版本
- 人：执行人 + 确认人 + 出单人

**为什么必须有**：结论 = f(代码, 库结构, 通道, 人)。前三样任一变了，这张单就不成立了；没有指纹，报告会在半年后被拿着说"当时你们说过能上"。

### 3.5 什么落库、什么不落库（既有铁律的边界）

出单**之前**的一切计算都是读取期现算，不落库（归因、分类候选、覆盖率、影响面）。出单**那一刻**的结果固化落库——那不是缓存，是留痕，之后不许被重算覆盖。两条规则不冲突，分界就是 `status: draft → issued`。

## §4 生成流程（六步，全程零写入目标库）

| 步 | 做什么 | 复用哪个已有零件 |
|---|---|---|
| 1 圈范围 | 区间内的提交 + 涉及的仓库 | `commits`/`file_changes`，即 ReleaseController.java:45-48 |
| 2 聚目标 | 提交 → 受影响目标（接口卡/SQL 卡/分发服务），带 basis 精度 | `commit_targets`（语句粒度归因，V16 注释就是为这一秒写的） |
| 3 找证据 | 每个目标查启用用例 + 区间内/最近的执行记录（带 commit_id） | `test_cases` + `test_runs` idx_runs_target/idx_runs_commit |
| 4 校前提 | 用例参数的"数据前提"在目标库只读复核：那行还在吗、状态还是它假设的那个吗 | 只读取值服务 + `column_value_cache` + `table_meta`（零写入三件套：只读连接 + 写死的 SELECT + 标识符过白名单再绑定） |
| 5 指嫌疑 | 失败目标 → 区间内动过它的提交 + 历史上最近一次通过点 + diff 引用 | `baselineDiff`（TestRunService.java:271-294）+ `/cases/{id}/set-baseline`（TestController.java:393） |
| 6 固化 | 算指纹、写 `report_rows`/`report_gaps`、`status=issued` | 新增 |

第 4 步是"假失败"能被分出来的唯一理由，也是本系统独有的能力（外部工具无法在不写库的前提下证明数据漂移）。第 4 步**不重跑任何存储过程、不建表、不改任何一行**：只读连接 + 写死的 SELECT + 标识符过白名单再绑定。

## §5 结论行分类与定性规则

三类，互斥：

| 分类 | 判据 | 系统怎么自证 |
|---|---|---|
| **代码问题** | 断言不过，且前提校验确认数据没变 | 只读校验通过 + 同参数在旧 commit 上曾通过 → 指向区间内动过该目标的提交 |
| **数据前提不成立** | 用例假设的那行没了/状态变了/字典项变了 | 只读回读出实际值，与用例假设并排展示（不是猜，是查到的） |
| **环境或通道问题** | 连不上、登录流过期、驱动/权限缺失 | 复用 11 项可测性体检结论，不另造判据 |

**定性规则（用户答"1，2"后合成的那一条，全文只有这一处需要人确认的例外）**：

> **自动定性、直接入报告、每行可改判、改判留痕；只有一种情况必须人确认——证据不足时系统不许猜，那行老实挂 `pending`（待定）并计入风险声明。**

"假失败区分"是报告可信度的地基，不是便利功能：一旦有一行分类是编的，整份单子的"上线依据"资格就作废。

**跟"未闭环缺陷"是两回事，都要留**：现有的 `countFindings`（ReleaseController.java:80-84，查 `findings` 表 open/confirmed）回答"这里已知有坑没填"，三分类回答"这一次失败怪谁"。结论行两边都要带，不许用一个盖掉另一个——一张只报失败分类、不报未闭环缺陷的单子，等于把他已经在管的缺陷清单弄丢了。

## §6 三种出口 = 一份数据三种渲染

现有 HTML 导出是**界面另存**（字符串拼 HTML，ReleaseController.java:170-193），不是从结构化结论渲染。这个区别决定第三项交付物（喂给别的系统）能不能成立，所以必须反过来：

```
report_rows + report_gaps（唯一事实源）
   ├─→ HTML：给人看/打印存档，每行含"点回证据"链接
   ├─→ JSON：字段固定、逐行 evidence_id，外部系统可直接消费
   └─→ 不可变快照：issued 后落盘，v2 不改 v1
```

**JSON 契约要点**：字段名固定不随界面文案变；每个 `row` 必带 `run_id`（可为 null，但必须显式为 null 而不是缺字段）；`classification` 与 `overrides` 同时输出（外部系统要看得到"系统原判"和"人改判"是两个事实）；顶层带 `fingerprint` 全文。三渲染**同一数据源**，HTML 不许自己再算任何数。

## §7 边界与诚实条款（8 条，逐条都是"骗人会死"的那种）

1. 区间内**一个提交都没学到**（无 commit_targets 行）→ 报"区间不可判定"，**不出空报告**。空报告比报错危险得多。
2. 归因 basis=`file`（只能到整文件，碰不到语句行）→ 该行必须标粗归因，不许与 line 级混排看不出区别。
3. 前提校验没跑成（超时/权限/表不在）→ 该行只能 `pending`，**不许默认算 pass**。
4. 环境不可达 / 登录流过期 → 整单标"本轮未执行"，**绝不输出 READY**。
5. 值失效（参数候选值过期）归入 `report_gaps` 的 `value_expired`，**不算用例失败**（沿用既有口径："场景要求留空"与"用户手滑清空"是两种状态，不许混成一个）。
6. 未被任何用例命中的目标**必须出现在报告里，不许过滤掉**——影响清单是"该测什么"的答案，不是"我测了什么"的成绩单。
7. 改判必须填理由，`overrides_json` 追加不覆盖，出单人与改判人分开显示。
8. 报告上恒显指纹原文 + 一句时效声明："本结论仅对上述指纹成立，之后代码或库结构任一变化即不成立。"

## §10 明确不做（红线与同质化）

- **自动往目标库写数据/造数/改结构**：红线，不动。找数据只做到"只读查到并给你看候选"，填不填由人点。
- **schema 变更、建表、重跑存储过程做校验**：同上。
- 多语言静态解析大饼：等真来了某个栈的项目，再做那一个解析器，不提前摊开。
- 更花哨的请求编辑器 / 响应树美化 / 场景矩阵自动生成：红海且无独有资产支撑。
- 首页看板类炫技可视化：往后放，不列入本路线。

## §11 与另两条发想的关系（本轮同时提过，暂不开工）

- **场景值自动带入接口参数与 ③ 条件参数**：它是本报告**证据层的入口**。断点在 `app.js:2937` 的 `bindSqlCase()`——【到测试台打开】只带了用例身份（id/name/commitId），没带 `params`；而【▶ 执行这条】用的是完整 `test_cases.params`。两个按钮走两套事实，就是用户截图里那个疑问的根因。这件事小而立刻见效，适合插在任何一批之前。
- **学习任意架构（微服务/其它语言/老式 Web）**：它是本报告能成立的**前置条件**——认不出目标就聚不出结论行。第一批只要求一条纪律：**认不出来说认不出来**（与"界面不许装懂"同一类错误），解析器按栈增量补，不提前摊。
