# PreFlight · 半自动测试系统 · 解决方案

> 版本：v0.2（Java 单体 / 非 Docker 定稿）
> 日期：2026-09-19
> 项目代号：PreFlight——取自航空"起飞前检查"（preflight check），寓意每次上线前由系统完成一遍系统性检查，把问题拦在起飞之前
> 配套文档：《02-概要设计》《03-开发计划》

---

## 1. 背景与痛点

项目由多名开发人员协作完成，各自提交代码后的自测情况参差不齐，导致：

1. **改动不可见**：没有系统能回答"这次提交改了哪些文件、动了哪些接口、可能影响什么"。
2. **自测不可控**：自测质量依赖个人习惯与经验，缺少统一的验证手段。
3. **测试资产不沉淀**：每次测完即丢，用例、参数、经验无法复用与积累。
4. **测试环境成本高**：很多验证只是为了确认一条 SQL、一个接口，却要完整启动被调服务。

目标：建设一套**半自动测试系统**，以"学习项目 → 感知改动 → 归纳影响 → 生成用例 → 人工确认并执行 → 沉淀资产"为闭环，在上线前拦截问题，给最终用户稳定体验。

## 2. 建设目标与边界

### 2.1 目标（对应需求的六项能力）

| # | 能力 | 一句话描述 |
|---|------|-----------|
| 1 | 项目自主学习 | 指定前端/后台/数据库等多个项目目录，系统借助大模型摸清项目结构与接口交互，能自主构造登录、接口调用等请求 |
| 2 | 改动感知与测试 | 检测文件改动，生成改动摘要与影响接口清单，自动写测试用例并生成请求 Demo；页面按接口定义**动态生成测试表单**，填参即可调用 |
| 3 | 免启动直测 | 对简单改动（如仅改 SQL 出入参），**不启动被调服务**即可直连数据库验证 SQL / 存储过程 |
| 4 | 远程联测 | 需要起服务时，填写接口地址，系统按学到的登录流程自动登录并携带会话完成测试 |
| 5 | 大模型可配置 | 页面配置 LLM 供应商（支持多个），可切换、可设默认、可降级 |
| 6 | 知识落盘与离线 | 所有学习成果持久化、可导出迁移；部署到**不能联网**的环境时，凭既有知识仍可完成主要测试功能 |

补充约定（2026-09 二次确认）：

- **仓库接入同时支持 Git 与 SVN**：可填远程地址自动拉取更新（Git 走 JGit，SVN 走 SVNKit），也支持仅监听本地目录。
- **更新点全部留痕**：每次同步到的提交/版本、文件级改动一律入库且不可覆盖，作为增量学习与测试的依据。
- **已测/未测标记**：每条改动可标记"已测 / 部分测 / 未测 / 跳过"，**不强制全测**——由测试人员自行决定测哪些，未测项在改动流中醒目展示、可随时过滤回看。

### 2.2 非目标（明确边界，避免范围失控）

- **不替代**完整自动化测试平台（性能测试、UI 端到端自动化、全量回归流水线不在一期范围）。
- **不承诺 100% 拦截缺陷**。定位是"半自动 + 人在回路"：系统负责学习、归纳、生成、执行，**人负责确认关键判断**（影响面是否正确、用例是否合理、是否允许写库提交）。
- 一期不覆盖：移动端 App、消息队列/定时任务类异步链路的自动测试（列入后续演进）。

### 2.3 已确认的技术约束（2026-09 定稿）

1. **不使用 Docker**：以"自包含部署包 + 启停脚本"方式部署，目标机解压即用、零安装（详见《02-概要设计》§8）。
2. **后端 Java 单体**：单个 Spring Boot fat jar 承载全部能力；前端为 Vue3 单页应用，构建产物内嵌 jar，运行期无 Node 依赖。
3. **工具链隔离**：构建与运行统一使用 `tools/` 目录内 JDK 21（Temurin 21.0.12，已验证）+ Maven 3.9.11（含华为云镜像），仅在脚本与命令中进程级指定 `JAVA_HOME`，**不改动开发机既有 JDK 1.8 环境与任何系统变量**；部署包自带便携 JRE，目标服务器同样零安装。
4. **启停脚本与部署文档为正式交付物**：Windows（bat）/ Linux（sh）启停脚本随 M0 脚手架落地、M5 随部署包收口；《部署运维手册》随 M5 交付。

## 3. 可行性分析（逐条回应）

**总体结论：六项能力均可实现，无需技术上的"不可行"妥协；风险主要在 LLM 准确率与特殊环境的登录流程，均有工程兜底手段。**

### 能力 1：项目自主学习 —— 可实现，但要"分层学习"

- 做法：静态解析（JavaParser / JSqlParser 等语言专用解析器 + 框架识别规则）打底，LLM 负责归纳提炼，两者结合而非纯靠 LLM 读代码。
  - 后台：识别 Controller / 路由 / Service / Mapper(DAO)，提取**接口卡**（路径、方法、入参、出参、鉴权方式、涉及的表）。
  - 数据库：解析建表语句、存储过程、函数定义，提取**数据对象卡**（签名、出入参）。
  - 前端：识别路由、API 调用清单，与后台接口做交叉印证（前端调了哪些接口 → 反推接口重要度）。
- 关键点：**人工确认环节**。LLM 提取的接口卡先以"草稿"状态入库，人确认后生效，避免幻觉直接污染知识库。每条知识带**置信度**。
- 风险：超大仓库首次学习耗时。对策：按目录增量索引 + 过滤规则 + 分批学习，学习任务后台异步执行。

### 能力 2：改动感知与测试 —— 可实现，是本系统的核心闭环

- 改动检测：定时轮询 `git fetch`（或仓库 webhook），解析新 commit 的 diff。
- 改动摘要：diff → LLM 生成"人话摘要"（改了什么、为什么可能改、风险点）。
- 影响分析：靠**文件级映射表**（学习阶段建立"源文件 ↔ 接口/SQL"的行级归属关系），把改动文件映射回受影响的接口与数据对象，不依赖 LLM 猜。
- 测试用例：LLM 基于接口卡 + diff 生成用例（正常值、边界值、异常值），落地为**参数模板**。
- 动态测试页：接口卡的入参 schema → JSON Schema → 前端表单渲染器自动生成表单。接口形式不同（GET/POST/PUT、query/body/path 参数）都由 schema 描述，页面无需硬编码。**可实现，且是本方案体验最好的部分。**

### 能力 3：免启动直测 —— 可实现，且有明确技术路径

- 场景本质：改动只发生在 SQL 层（如 MyBatis mapper XML、注解 SQL、存储过程）时，跳过 Java/Node 服务，直接对数据库验证。
- 做法：
  1. 学习阶段把 mapper XML / SQL 注解 / 存储过程**还原为可执行 SQL 模板**（含参数占位符）。
  2. 测试时动态表单填参 → 参数绑定执行 → 展示结果集/影响行数。
  3. **默认包在事务里执行，测试完 ROLLBACK**，不污染数据；确需提交的（如 DDL 验证）二次确认后执行。
- 存储过程：直接 `CALL / EXEC`，出入参同样由学习阶段提取的签名生成表单。
- 风险：目标库是生产库时的安全。对策见《02-概要设计》安全设计（只读账号建议、黑名单语句、行数/超时限制、审计）。

### 能力 4：远程联测 + 自动登录 —— 可实现，验证码是唯一硬点

- 做法：学习阶段提取登录流程（登录接口、参数、响应结构、token 存放位置），保存为**登录流**配置。测试执行前先跑登录流拿会话（Token/Cookie），自动注入后续请求。
- 会话过期自动重登；多环境（测试/预发）各配一套地址与账号。
- 硬点：图形验证码/短信验证码/企业 SSO 跳转。对策：① 验证码提供人工兜底（弹窗让人输入一次，会话复用）；② 不少测试环境本身关闭验证码；③ SSO 场景支持"手动登录一次，系统接管 Cookie"。

### 能力 5：LLM 多供应商页面配置 —— 可实现，纯工程问题

- 统一走 OpenAI 兼容协议适配（市场主流皆支持），另加本地模型（Ollama / vLLM）适配。
- 页面可配置多个供应商：名称、Base URL、API Key（加密存储）、模型名、温度、启用状态、默认项。
- 网关能力：按用途路由（摘要用便宜模型、生成用例用强模型）、失败自动切换备用供应商、Token 用量统计。

### 能力 6：知识落盘、迁移、离线可用 —— 可实现，设计时就要"一切皆文件"

- 所有知识（接口卡、SQL 模板、登录流、用例、改动历史、LLM 输出缓存）落盘为 **SQLite + 文件 + 本地向量索引**，一个项目一个可导出的**知识包（zip）**，拷贝即迁移。
- 离线场景四层保障：
  1. **模板化用例**：学习阶段已生成的用例是纯数据，不依赖 LLM 即可执行。
  2. **LLM 输出缓存**：联网时的 LLM 结果按请求指纹缓存，离线后相同请求直接命中。
  3. **本地 Embedding**：向量检索用本地模型（如 bge 系列离线运行），知识检索不依赖云。
  4. **降级模式**：LLM 完全不可用时，改动摘要退化为结构化 diff 报告，测试功能（动态表单 + HTTP/DB 执行）完全不受影响——因为执行引擎本来就不依赖 LLM。

## 4. 总体思路：一条闭环 + 三种测试模式

### 4.1 核心闭环

```
        ┌──────────────────────────────────────────────┐
        │                                              │
        ▼                                              │
  [① 学习] 指定项目目录 → 静态解析 + LLM 归纳            │
        → 接口卡/数据对象卡/登录流（人工确认入库）        │
        ▼                                              │
  [② 感知] 轮询/钩子捕获新提交 → diff                    │
        ▼                                              │
  [③ 归纳] 改动摘要 + 影响接口清单（文件映射，非猜测）     │
        ▼                                              │
  [④ 用例] LLM 生成候选用例（含离线模板）                │
        ▼                                              │
  [⑤ 执行] 人确认参数 → 点击测试 → 结果/断言/耗时         │
        ▼                                              │
  [⑥ 沉淀] 用例入库、结果留痕、知识库更新 ────────────────┘
```

### 4.2 三种测试模式（对应能力 3、4、6）

| 模式 | 触发条件 | 是否需要起被调服务 | 说明 |
|------|---------|------------------|------|
| **DB 直测** | 改动仅为 SQL/存储过程/仅涉及出入参变化 | 否 | 直连数据库参数绑定执行，事务回滚保护 |
| **HTTP 远程测** | 改动涉及业务逻辑、必须经过服务 | 是 | 填服务地址，系统自动登录后调用 |
| **Mock 回放**（增值项） | 服务不可用 / 离线环境 | 否 | 录制过的真实响应回放，验证请求构造正确性 |

三种模式共用同一套**动态测试表单**与**用例资产**，用户按改动类型选择或由系统建议。

### 4.3 半自动的设计哲学

- **系统建议，人拍板**：影响面、用例、是否提交写库，全部先给建议，人确认后生效。
- **可解释**：每条结论都带证据（来源文件、行号、置信度），不输出"黑盒判断"。
- **可干预**：任何自动生成的产物（摘要、用例、接口卡）都可人工编辑，编辑结果优先级高于 LLM。

## 5. 关键使用场景走查

**场景 A · 首次接入**：管理员注册项目，分别填入前端、后台、数据库三个目录 → 点"开始学习"→ 后台任务边解析边调 LLM → 完成后浏览接口清单、数据表、存储过程，确认草稿 → 系统已能自主发起登录与接口调用演示。

**场景 B · 日常提交**：开发小王提交了 3 个文件 → 系统轮询发现 → 页面出现改动卡片：摘要 + 影响接口 2 个 + 已生成 6 个候选用例 → 测试员打开动态表单，微调参数，点击测试 → 3 过 1 挂 → 发现边界值 bug → 上线前拦截。

**场景 C · 只改 SQL**：小李改了 mapper XML 里一条查询的出入参 → 系统判定"SQL 类改动"→ 标记"无需启动服务"→ 测试员在 DB 直测页填参数执行 → 事务回滚，结果即改即验。

**场景 D · 业务逻辑改动**：小张改了订单 Service → 系统判定需远程测试 → 测试员选择测试环境（已配地址）→ 系统按登录流自动登录 → 动态表单填参执行 → 断言结果。

**场景 E · 内网离线部署**：把知识包导出 → 拷入隔离网段系统 → 导入 → 接口清单、动态测试、DB 直测、模板用例全部可用；LLM 相关功能走缓存与降级模式。

## 6. 方案亮点与补充建议（我的想法）

以下是我在您需求之外的补充建议，按"建议一期做 / 二期做"标注：

### 6.1 建议一期纳入

1. **改动风险分级**（高/中/低）：按改动类型与影响接口数自动定级（改 SQL 出入参=低，改核心 Service=高），高风险改动在页面上置顶并强提醒，让有限测试精力花在刀刃上。
2. **用例资产沉淀**：每次执行过的用例（含参数与结果）自动入库，形成随时间越来越值钱的回归用例库；改动命中已有用例时优先推荐复用，而非重新生成。
3. **LLM 输出缓存**：相同 diff 指纹不重复调用 LLM——省钱、提速，且是离线能力的基石。
4. **凭据保险库 + 审计日志**：数据库密码、LLM Key 加密存储；谁在何时对哪个接口执行了什么，全程留痕。测试系统本身掌握大量敏感入口，安全必须第一天就做。
5. **人工确认工作流**：LLM 产物一律"草稿→确认→生效"，配置信度标识。这是对抗 LLM 幻觉最有效且成本最低的手段。

### 6.2 建议二期规划

6. **团队质量看板**：按人/按项目统计提交数、自测覆盖率（改动是否被测过）、发现问题数——把"自测情况各不相同"变成可视化管理动作。
7. **上线门禁**：可配置规则（如"高风险改动未测试不允许标记可上线"），把系统从工具升级为流程卡点。
8. **通知集成**：新改动、测试结果推送钉钉/企业微信/邮件，测试员不用盯着页面。
9. **夜间巡检**：定时批量执行回归用例库，防"老功能被新改动悄悄改坏"。
10. **敏感数据脱敏**：直测真实库时对返回的手机号、身份证等自动脱敏展示。

### 6.3 技术侧提示

- **代码外发合规**：若使用云端 LLM，代码片段会出网。方案支持本地模型（Ollama/vLLM）作为供应商之一，涉密环境直接全本地化。
- **新框架扩展**：解析器按"适配器"设计，主流框架（Spring Boot + MyBatis、Express/Nest、Django/FastAPI 等）先做覆盖，遇到新框架加适配器即可，不动核心。

## 7. 结论

您描述的六项能力没有原理性障碍，本质是"**静态分析打底 + LLM 归纳提炼 + 文件级影响映射 + 双通道执行引擎（DB 直连 / HTTP 远程）+ 一切落盘**"的组合。其中最能体现价值的两个设计决策：

1. **不把 LLM 当黑盒**：LLM 只做它擅长的（归纳、生成），影响分析和请求执行靠确定性工程手段，保证可靠与可离线。
2. **知识库是一等公民**：所有功能围绕知识库展开，知识库天然落盘、天然可迁移，离线能力是设计结果而非补丁。

建议按《03-开发计划》的里程碑推进，M1+M2（约 6 周）即可形成覆盖核心痛点的 MVP。
